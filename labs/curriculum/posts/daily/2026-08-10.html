為什麼要用框架：Vue的響應式系統怎麼讓畫面自己更新

技能實驗室・每日課程 2026-08-10 約 6 分鐘 對應真專案主題：Vue.js 基礎知識
⚡ 30秒白話版

框架要解決的核心痛點，是「資料變了、畫面要跟著變」這件事以前得全部手動做。沒有框架的年代，你改了一個數字，就得自己寫程式碼去找到畫面上對應的那塊元素、再手動改它的文字，資料一多就到處是這種同步的雜活，很容易漏改、改錯。Vue 的響應式系統（reactivity）把這件苦差事自動化：你只要把資料宣告成響應式的，Vue 會在背後偷偷記住「哪一塊畫面用到了哪些資料」——這個動作叫依賴追蹤；等你一改資料，它因為早就知道誰用到，就自動、而且只重繪用到的那一小塊畫面，你完全不用手動去碰 DOM。最容易答錯的一句：響應式不是魔法，對物件新增一個原本不存在的屬性、或直接用索引去改陣列的某一格，舊版 Vue 有時候會追蹤不到、畫面不更新。

SLIDE 1 簡報講解

這張圖在講的是，Vue 這種框架到底幫你省掉了什麼。左邊這張卡是沒有框架的世界：資料變了，你得自己寫程式碼去找到對應的畫面元素、手動改它，資料一多就到處是這種同步的雜事，很容易漏改、改錯。中間是 Vue 的核心觀念，響應式系統。你只要把資料宣告成響應式的，Vue 會在背後偷偷記住這塊畫面用到了哪些資料，這個記住的動作叫做依賴追蹤。右邊是重點：當你改了資料，Vue 因為早就知道誰用到它，就會自動、而且只重繪用到的那一小塊畫面，你完全不用手動去碰 DOM。所以整張圖的主張就是，框架把你從手動同步資料和畫面這件又煩又容易錯的事裡解放出來，你只要專心描述資料長什麼樣、畫面該長什麼樣，同步交給它。

壹、這是什麼

Vue 的響應式系統，是一套「你只改資料、畫面自己跟著改」的自動同步機制。先講它取代掉的那件苦差事：在還沒有前端框架的年代，畫面上顯示的東西和背後的資料是兩件各自獨立的事。你程式裡有一個變數叫「購物車數量」，畫面右上角也有一個顯示這個數字的小圖示，但這兩者之間沒有任何自動的連結。所以每次數量一變，你就得自己寫一行程式，去畫面上「抓到」那個小圖示、再把裡面的文字改掉。一兩處還好，等頁面變複雜、同一筆資料同時影響好幾個地方，這種手動同步的程式碼就會散落各處，而且非常容易漏掉某一處、造成「資料明明是 3、畫面卻還顯示 2」的錯誤。

響應式系統的做法，是讓資料和畫面之間自動建立一條看不見的線。你只要把資料宣告成「響應式的」，Vue 就會在你的畫面第一次讀取這筆資料時，偷偷記下一件事：「這一塊畫面用到了這筆資料」——這個記住的動作，術語叫依賴追蹤（dependency tracking，也就是搞清楚誰依賴誰）。之後只要你一改這筆資料，Vue 因為早就知道有哪些畫面用到它，就會自動去更新、而且只更新用到它的那一小塊，沒用到的地方完全不動。原理上，這是靠攔截資料的「讀」和「寫」做到的：讀的時候記下「是誰在讀」，寫的時候就通知「剛才那些讀過的人，你們該更新了」。你要做的只剩下描述「資料長怎樣、畫面對應該長怎樣」，中間的同步全部交給框架。

貳、為什麼業界在乎

業界在乎響應式，是因為它直接決定了前端開發的「可維護性」——也就是團隊能不能長期快速改東西而不出包。104 人力銀行《AI 人才趨勢報告》反覆強調的重點，是求職者要能打通「從需求到能上線」的完整應用情境，而不是只會零散語法。放到前端，響應式正是這個完整情境裡最底層的一塊：一個真實產品的頁面，同一筆資料往往同時牽動好幾處畫面（購物車數量同時影響右上圖示、結帳頁小計、免運進度條）。如果靠人工同步，每加一個新畫面就要記得回頭補一行同步碼，人一多、需求一急，必然有人漏掉，於是「畫面和資料對不上」的 bug 就層出不窮。

把同步這件事交給框架自動處理，換來的是兩個業界最實際的好處。第一是少一整類 bug：既然沒有人再手動同步，「忘了更新某一處畫面」這種錯誤從源頭就消失了，這類 bug 在人工時代大概是前端最常見、也最惱人的一種。第二是開發速度與分工：工程師的心力可以從「畫面怎麼跟資料同步」這種瑣事，移到「這個功能的邏輯與資料該怎麼設計」上，這正是報告說的、把技能連成完整情境而不是卡在零碎操作。這也是為什麼今天你幾乎找不到不用框架的大型前端專案——Vue、React 這些框架的存在理由，某種程度上就是「把響應式這件事做好」。

參、實務怎麼用

放到金融或電商場景，最貼近的例子是玉山或國泰網銀的一個「帳戶總覽頁」。這種頁面上，同一筆「帳戶餘額」資料常常同時出現在好幾個地方：頁面上方的大數字、下方的可用額度、以及某個「是否足夠轉帳」的提示。使用者做完一筆轉帳後，餘額變了，這三處都得跟著變。如果我用純手工同步，就要記得在轉帳成功的程式裡，一個一個去改這三處，只要漏了一處，畫面就會出現「上面顯示扣款後、下面還是舊餘額」這種在金融產品裡會嚴重打擊信任的錯誤。用 Vue 的做法是：我把「帳戶餘額」宣告成一筆響應式資料，畫面上那三處都直接綁定它；轉帳成功後，我只需要把這一筆餘額資料更新成新值，那三處畫面就會自動、同時跟著變，我完全不必去碰任何一處的顯示邏輯。少寫的那些手動同步碼，正是少掉的那些出錯機會。

對我這種法律金融跨域背景的人，最能講出差異化的一點，是把「響應式」連到資料的單一真實來源（single source of truth，意思是一筆事實只存一份、別處都引用它）。這其實和我熟悉的合規思維是同一個腦迴路：一份合約條款如果在三個文件裡各抄一份，早晚會出現三個版本互相矛盾；正確做法是只存一份正本、其他地方都引用它。響應式資料在前端扮演的就是這個「正本」——餘額只有一個真值，畫面所有顯示它的地方都是這份真值的投影，改真值、投影自動跟上，你不會有「同一個數字在頁面上出現兩種版本」的風險。這種「先把真實來源定義乾淨、再讓顯示自動追隨」的思路，是我背景比較能第一時間對上的一層。放到國際遠端全端職缺，同一組觀念會延伸到前後端一致性：前端響應式解決「畫面跟資料同步」，但畫面的資料本身還得跟後端的真值同步，這是我接下來要打通的下一段。

肆、常見誤區或追問延伸

最容易答錯、也最容易在實作踩到的地方，是以為「只要資料是響應式的，我怎麼改它畫面都會更新」。這是把響應式當成無所不知的魔法。真相是：Vue 的追蹤有它的邊界。以較早的 Vue 2 為例，它是靠一種攔截既有屬性讀寫的機制來追蹤的，所以如果你對一個響應式物件新增一個原本不存在的屬性，或用索引直接改陣列的某一格（例如 arr[1] = 新值），這些操作它當時攔截不到，資料變了、畫面卻不會更新，得改用特定的 API 才行。Vue 3 換了底層機制（用的是一種能攔截更多操作的代理機制）後大幅改善了這類問題，但這個坑本身很經典，面試官很愛用它來確認你是「真的懂追蹤怎麼運作」，還是只把響應式當黑盒。這裡我要誠實：這個原理和踩雷情境我搞懂了、也能講清楚為什麼會這樣，但我目前是從教學專案和小型 side project 上練的，還沒有在大型 Vue 產品裡處理過複雜的響應式效能與更新時機問題（例如一次改很多筆資料時的批次更新、或深層巢狀資料的追蹤成本），被追問到這種實戰細節時，我會講清楚我掌握的主線並說明我會怎麼查證，而不是硬掰經驗。

另一個值得先想清楚的追問，是「響應式」和「雙向綁定」不是同一件事。很多人會把 Vue 的 v-model（讓表單輸入和資料自動雙向同步的語法）當成響應式的全部，其實雙向綁定只是把響應式再包一層方便寫表單的糖：底層還是「輸入改了 → 更新響應式資料 → 資料改了 → 更新畫面」這條追蹤鏈。把兩者分清楚，才不會在被問到「v-model 背後發生什麼」時，只答得出表面用法、答不出它其實是響應式加上一個事件回填。

用框架的第一個理由，從來不是「它比較潮」，而是「它幫你把資料和畫面之間那條要人工維護的線，自動接了起來」——想清楚這一點，你就抓到了響應式系統存在的全部意義：你只管把資料改對，剩下的畫面，讓它自己跟上。

🎤 面試官可能怎麼問
  1. 「為什麼要用 Vue 這種框架？它到底解決了什麼？」 👉 這題其實在問：你懂不懂框架存在的根本理由，還是只會用它的語法。 她可以怎麼答：它解決的是「資料變了、畫面要跟著變」以前得全部手動做的問題。沒有框架時，我改一個變數，就得自己寫程式去畫面上找到對應的元素、手動改它，資料一多這種同步碼就散落各處、很容易漏改造成畫面和資料對不上。Vue 的響應式系統把這件事自動化：我把資料宣告成響應式，Vue 會做依賴追蹤，記住哪塊畫面用到哪筆資料，我一改資料它就自動、且只重繪用到的那一小塊。所以框架的價值是讓我專心描述資料和畫面的關係，同步交給它，少掉一整類「忘了更新某處」的 bug。
  2. 「Vue 的響應式是怎麼知道『該更新哪裡』的？」 👉 這題其實在問：你懂不懂依賴追蹤的運作，而不只是會用。 她可以怎麼答：靠攔截資料的讀和寫來做依賴追蹤。當畫面第一次讀取某筆響應式資料時，Vue 會記下「是這一塊畫面在讀它」，等於建立一條「這塊畫面依賴這筆資料」的關係；之後只要有人寫入、改了這筆資料，Vue 就去通知所有依賴它的畫面「你們該更新了」，於是只重繪用到它的那些地方，沒用到的完全不動。簡單說就是：讀的時候記下誰在讀，寫的時候通知剛才那些讀過的人。
  3. 「你改了響應式資料，畫面卻沒更新，可能是什麼原因？」 👉 這題其實在問：你知不知道響應式追蹤是有邊界的、不是魔法。 她可以怎麼答：最經典的原因是改的方式超出了追蹤的攔截範圍。以 Vue 2 為例，它靠攔截既有屬性的讀寫來追蹤，所以如果我對一個響應式物件新增一個原本不存在的屬性、或用索引直接改陣列的某一格，它當時攔截不到，資料變了畫面卻不動，得用特定 API 才行。Vue 3 換成代理機制後大幅改善這類問題。我會先確認資料到底有沒有真的變、是不是用了追蹤不到的方式去改，而不是先懷疑框架壞掉。
  4. 「v-model 的雙向綁定，背後其實發生了什麼？」 👉 這題其實在問：你分不分得清雙向綁定和響應式的關係。 她可以怎麼答：v-model 不是另一套魔法，它是把響應式再包一層方便寫表單的語法糖。底層還是同一條追蹤鏈：使用者在輸入框打字，觸發一個事件去更新對應的響應式資料，資料一改，響應式系統就自動更新畫面。所以它其實是「畫面到資料」和「資料到畫面」兩個方向接在一起——一個是事件回填資料，一個是響應式更新畫面。把這兩層拆開講，才顯得我是真的懂它怎麼運作，而不是只會寫 v-model 三個字。
  5. 「在一個帳戶總覽頁，同一筆餘額顯示在很多地方，你會怎麼設計？」 👉 這題其實在問：你能不能把響應式接回完整業務情境與資料一致性。 她可以怎麼答：我會把「帳戶餘額」設計成單一的響應式資料，當作這個數字的唯一真值，畫面上顯示它的每一處——上方大數字、可用額度、能不能轉帳的提示——都直接綁定這一筆。轉帳成功後我只更新這一筆餘額，那幾處就會自動同時跟上，不會出現上面扣了、下面還是舊值的不一致。因為我有金融合規背景，我特別在意這種單一真實來源的設計：一筆事實只存一份、別處都引用它，就像合約只留一份正本，才不會出現同個數字在頁面上有兩種版本。
