為什麼密碼不能直接存：雜湊、鹽值與權限認證的最低防線

技能實驗室・每日課程 2026-08-18 約 8 分鐘 對應真專案主題：Python：網站安全與權限認證
⚡ 30秒白話版

使用者的密碼絕對不能明文（原始文字）直接存進資料庫，因為資料庫一旦被偷走或工程師隨手一看，所有人的密碼就全裸奔。正確做法有三層：第一層是存雜湊（把密碼經過一個「只能算過去、很難算回來」的單向函數，變成一串固定長度的亂碼）；第二層是加鹽值（每個帳號配一段隨機字串一起雜湊，讓兩個人就算用同一組密碼、存進去也長得不一樣，攻擊者預先算好的彩虹表就查不到）；第三層是選一個故意算得慢的密碼專用演算法（例如 bcrypt），讓想暴力硬猜的人一秒只能試幾次、划不來。一句話心法：密碼不是拿來「存」的，是拿來「驗證」的——系統永遠只比對雜湊，從來不需要知道你的原始密碼。

SLIDE 1 簡報講解

這張圖在講的是，為什麼使用者的密碼絕對不能明文直接存進資料庫。左邊是最糟的做法：直接存原始密碼，資料庫一外洩，所有人的密碼就全裸奔，連自家工程師都看得到。中間是第一層改善——雜湊，把密碼經過一個單向函數，變成一串固定長度的亂碼，理論上很難算得回去。但光雜湊還不夠，因為兩個人用同一組密碼會得到一樣的結果，攻擊者可以用預先算好的彩虹表反查。所以右邊要加上鹽值，每個帳號配一段隨機字串一起雜湊，同樣的密碼也會存成不同結果，彩虹表就失效了。最後還要用專門對付密碼的慢雜湊演算法，像 bcrypt，故意算得慢一點，讓暴力破解划不來。整張圖的主張是：密碼不是拿來存的，是拿來驗證的。

壹、這是什麼

「密碼不能直接存」的意思是：資料庫裡不該出現使用者的原始密碼，該存的是它經過雜湊（把一段文字丟進一個「只能算過去、很難算回來」的單向函數，得到一串固定長度的亂碼）之後的結果。你可以把雜湊想成「絞肉機」——把一塊肉絞成肉泥很快，但沒有人能從一盤肉泥還原出原本那塊肉的形狀。同一塊肉每次絞出來的肉泥都一樣，所以要驗證你輸入的密碼對不對，系統不用知道你的原始密碼，它只要把你這次輸入的密碼「再絞一次」，看絞出來的肉泥跟當初存的那份是否一模一樣就好。

但單純雜湊有個罩門：同樣的密碼會算出同樣的亂碼。這代表如果很多人都用「abc123」，資料庫裡他們那一欄會長得一模一樣；而攻擊者早就把常見密碼的雜湊值全部預先算好、做成一張對照表（這種預先算好的反查表叫彩虹表），資料庫一外洩，他拿你的亂碼去表裡一查就還原了。解法是鹽值（salt，替每個帳號隨機產生一小段字串，跟密碼拼在一起再雜湊）：這樣就算兩個人密碼相同，因為鹽不同，存進去的亂碼也完全不同，攻擊者沒辦法用一張通用的彩虹表一次打穿所有人。再往上一層，密碼專用的演算法（例如 bcrypt）還會故意設計得很慢、可調難度，讓想用電腦一秒硬猜幾百萬次的暴力破解變得不划算。這三件事——雜湊、鹽值、慢演算法——合起來就是存密碼的最低防線。

貳、為什麼業界在乎

業界在乎這件事，是因為它是「安全事故從尷尬變成災難」的分界線。任何有登入功能的系統，資料庫外洩幾乎是遲早要面對的風險；差別在於外洩之後傷害有多大。如果你只存了「加鹽的慢雜湊」，攻擊者拿到的是一堆很難反推、又不能互相比對的亂碼，短時間內動不了；但如果你存的是明文、或只用了沒加鹽的快速雜湊，那等於把所有使用者的密碼直接送給對方。而且因為很多人習慣到處用同一組密碼，你這個站外洩，往往連累使用者的信箱、其他網站甚至銀行帳號——這也是為什麼密碼保護不只是「你家的事」。這些都是常識性的資訊安全知識，不是引用特定報告的數字，但它是後端與全端面試裡最基本、也最容易看出一個人有沒有安全意識的一題。

這也正好對上 104 人力銀行《AI 人才趨勢報告》一直強調的方向：求職者要能打通完整應用情境，而不是只會孤立的單一技能。權限認證就是「完整情境」裡很典型的一環——你不只是會寫一個登入表單、把帳密收進資料庫，而是能連起來想：密碼進來之後怎麼安全地存（雜湊＋鹽值）、使用者下次登入怎麼驗證（比對雜湊而非還原密碼）、登入成功之後憑什麼讓他一路暢行（session 或 token，也就是「你已經證明過身分了」的通行證）、以及誰能做什麼（授權／權限控管）。一個只會把帳密塞進資料庫就交差的人，和一個交之前會先問「這些密碼萬一外洩了，攻擊者能做什麼」的人，在面試桌上的差距非常明顯。前者是照著需求打字，後者是在對使用者的安全負責。

參、實務怎麼用

放到玉山網銀或 91APP 這類產品，假設我要做註冊與登入，我會這樣處理密碼。第一，註冊時我不會把使用者輸入的密碼原文存進去，而是交給一個成熟的密碼函式庫（例如 Python 生態常見的 bcrypt／passlib）去做「加鹽的慢雜湊」——這類函式庫會幫我自動產生隨機鹽、把鹽和雜湊結果一起打包存進資料庫的一個欄位，我不用自己拼字串、也不用另外開一欄存鹽。第二，登入時我不會試圖「把資料庫裡的密碼解出來跟使用者比」（根本解不出來，那正是重點），而是把使用者這次輸入的密碼，用同一套函式庫的驗證函式去跟存起來的雜湊比對，回傳的是「相符／不符」。第三，我絕對不會自己發明雜湊或加密演算法，也不會用 MD5、SHA-256 這種「快」的雜湊來存密碼——它們是設計來算校驗和的，快正是缺點，對暴力破解太友善；密碼要用「故意慢」的專用演算法。第四，登入成功後我會發一個 session 或 token 當通行證，之後每個請求驗這張通行證就好，不需要每次都重新輸密碼。

對我這種法律金融跨域背景的人，最能連回本業的一點，是把雜湊理解成「不可逆的存證，而不是可解開的保險箱」——這跟法律上「驗證」與「解密」是兩件事的直覺很像。做合規、做身分核對時，你要證明的往往是「這個人提供的資料跟當初登記的相符」，而不是「把當初登記的秘密再攤開來看一遍」。密碼雜湊做的就是這種「只驗真偽、不還原內容」的事：系統能確認你是本人，卻永遠不知道、也不需要知道你的原始密碼。這裡有個很重要、很多人會搞混的分界——雜湊不是加密。加密（encryption）是可逆的，設計上就是要能用鑰匙解回原文（適合存「之後還要讀出來用」的東西，例如要顯示的身分證字號）；雜湊是刻意不可逆的，適合存「只需要比對、不需要讀回」的東西，密碼就是典型。放到金融系統這點特別要命，因為帳戶密碼一旦處理錯，牽動的是真金白銀；放到國際遠端全端職缺，能講清楚「我為什麼這樣存密碼、外洩了會怎樣」也很加分——遠端協作沒辦法隨時當面解釋，一段你講得出安全考量的認證流程，本身就是專業度的證明。

肆、常見誤區或追問延伸

最容易踩、也最常被追問的坑，是把「雜湊」跟「加密」當成同一件事。很多人會說「我有把密碼加密再存」，但如果他用的其實是可逆的加密，那代表系統手上握有一把能把所有密碼解回原文的鑰匙——這把鑰匙一旦外洩，等於全部密碼一起外洩，跟明文的差別只是多一道手續。正確的講法是「密碼要用雜湊（不可逆）而不是加密（可逆）來存」，因為密碼我們永遠只需要「驗證相不相符」，根本不需要把它讀回來。如果面試官問「雜湊和加密差在哪」，能一句講出「加密是可逆、要能解回原文；雜湊是刻意不可逆、只能拿來比對」，就明顯是懂門道的答法。

另一個很值得先想清楚的追問，是「為什麼不能用 MD5 或 SHA-256 來存密碼？它們不是也很有名的雜湊嗎？」。乍看它們確實是雜湊、也算不回來，好像可以用。但問題正好出在它們太快：MD5、SHA-256 是設計來快速算檔案校驗和的，一張顯示卡一秒可以算天文數字次，這對想暴力硬猜密碼的攻擊者反而是大禮。存密碼要的是故意慢、還能隨硬體進步調更慢的專用演算法，例如 bcrypt、scrypt、Argon2，讓每一次猜測都貴到划不來。不過我要誠實說：這一題我知道原則、也能講清楚為什麼要加鹽、為什麼要用慢雜湊，但目前多是在自己的小專案裡用現成函式庫實作過註冊登入，還沒在真正大流量、要處理密碼外洩應變、輪替鹽值或升級雜湊成本這種生產環境情境裡實戰過；被追問到那個層級時，我會誠實說明我掌握的原理，並說我會怎麼靠成熟函式庫和官方安全指引（例如 OWASP 的密碼儲存建議）去落實與驗證，而不是硬掰經驗。

一個登入表單寫得出來只是入門，真正的分水嶺是你知不知道密碼進了資料庫之後該長什麼樣子：不是明文、不是可解回的加密，而是一份加了鹽、用慢演算法算出來、只能拿去比對卻永遠讀不回原文的雜湊。把這件事想清楚，你交出去的就不只是一個能登入的功能，而是一個就算哪天資料庫被偷走、也不會讓使用者的密碼直接裸奔的系統。

🎤 面試官可能怎麼問
  1. 「使用者的密碼你會怎麼存進資料庫？」 👉 這題其實在問：你有沒有最基本的安全常識，還是會傻傻地把密碼原文存下來。 她可以怎麼答：我絕對不會存原始密碼，那樣資料庫一外洩就等於把所有人的密碼直接送出去。我會存「加了鹽的雜湊」：把密碼經過一個單向函數變成一串很難反推的亂碼，而且每個帳號配一段隨機的鹽值一起算，讓就算兩個人密碼一樣、存進去也長得不一樣。實作上我會用成熟的密碼函式庫，例如 bcrypt，它會自動幫我產生鹽、把鹽和雜湊打包存好。登入時我不是把密碼解回來比，而是把使用者這次輸入的密碼再雜湊一次，去跟存的那份比對是否相符。
  2. 「雜湊和加密差在哪？」 👉 這題其實在問：你分不分得清「可逆」跟「不可逆」，這是很多人會混的基本觀念。 她可以怎麼答：最關鍵的差別是可不可逆。加密是可逆的，設計上就是要能用鑰匙把密文解回原文，適合存那種之後還要讀出來用的東西。雜湊是刻意不可逆的，只能算過去、很難算回來，適合存那種只需要比對、不需要讀回原文的東西。密碼就是典型的後者——我們永遠只需要驗證使用者輸入的對不對，根本不需要把原始密碼讀回來，所以密碼要用雜湊，不是用加密。如果拿可逆的加密存密碼，那把解密鑰匙一旦外洩，等於全部密碼一起外洩。
  3. 「為什麼要加鹽值？只做雜湊不行嗎？」 👉 這題其實在問：你知不知道「同密碼同雜湊」這個罩門，以及彩虹表怎麼利用它。 她可以怎麼答：只做雜湊的罩門是，同樣的密碼會算出同樣的亂碼。所以如果很多人都用常見密碼，他們那一欄會長得一模一樣；而攻擊者早就把常見密碼的雜湊值預先算好做成對照表，也就是彩虹表，資料庫一外洩，拿亂碼去表裡一查就還原了。加鹽就是每個帳號配一段隨機字串一起雜湊，讓相同的密碼也存成完全不同的亂碼，這樣攻擊者就沒辦法用一張通用的彩虹表一次打穿所有人，只能對每一筆單獨慢慢算，成本大幅提高。
  4. 「那用 MD5 或 SHA-256 來存密碼可以嗎？」 👉 這題其實在問：你知不知道存密碼要「故意慢」，而不是挑一個有名的雜湊就好。 她可以怎麼答：不建議，問題出在它們太快。MD5、SHA-256 是設計來快速算檔案校驗和的，一張顯示卡一秒可以算天文數字次，這對想暴力硬猜密碼的攻擊者反而是大禮。存密碼要的是故意慢、還能隨硬體進步調更慢的專用演算法，例如 bcrypt、scrypt 或 Argon2，讓每一次猜測都貴到划不來。所以選演算法的直覺剛好相反：算校驗和要挑快的，存密碼要挑慢的。
  5. 「使用者登入成功之後，怎麼讓他接下來的操作不用每次重打密碼？」 👉 這題其實在問：你懂不懂認證（你是誰）之後還有「維持登入狀態」這件事，也就是 session 或 token。 她可以怎麼答：登入成功、也就是驗證過身分之後，我會發一張通行證給他，常見的做法是 session 或 token。之後每個請求他帶著這張通行證，伺服器驗這張證有效、沒過期就放行，不用每次都重新輸密碼。session 通常是伺服器記著狀態、發一個 id 給瀏覽器；token 例如 JWT 則是把身分資訊簽章後交給前端保管、伺服器驗簽章。老實說這一塊我目前主要是在自己的專案裡用框架內建的機制實作過登入狀態，token 過期、換發、被盜用怎麼防這些更細的取捨我還在累積，但基本的流程和它在解決什麼問題我是清楚的。
