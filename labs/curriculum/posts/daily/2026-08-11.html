React的資料流向：從useState到跟後端API溝通的完整路徑

技能實驗室・每日課程 2026-08-11 約 7 分鐘 對應真專案主題：React 資料串接與應用
⚡ 30秒白話版

React 的核心規矩只有一句：畫面是照著狀態畫出來的，你想改畫面，就去改狀態，不要自己去動畫面。useState 給你兩樣東西——一筆「狀態」（會影響畫面的資料）和一個「專門改它的函式」（一般叫 setXxx）。你不能直接改那筆資料，一定要透過這個函式改，React 才知道「資料變了、該重畫了」。這條資料流是單向的：狀態流向畫面，使用者的操作（例如點按鈕）觸發事件、事件回頭呼叫函式去改狀態，繞成一個循環。跟後端串接也走同一條路：畫面一載入，你在 useEffect（負責處理「渲染之後要做的事」的鉤子）裡發出 fetch 去打 API，拿到資料後一樣用 setState 把它塞進狀態，畫面就自動更新。最容易答錯的一句：狀態更新是非同步的，你呼叫 setCount 後馬上去讀那個變數，讀到的還是舊值。

SLIDE 1 簡報講解

這張圖在講的是，React 裡資料是怎麼流動的。左邊是核心：useState 給你一個狀態，還有一個專門用來改它的函式。畫面是照著狀態畫出來的，所以你想改畫面，不能直接去動畫面，而是呼叫那個函式去改狀態，React 才會重新渲染。中間這條線很重要：資料是單向流動的，從狀態流到畫面，使用者的事件再回頭呼叫函式去改狀態，繞成一個循環。右邊是跟後端串接：畫面一載入，你在 useEffect 裡發出 fetch 去打 API，拿到回傳的資料後，一樣是呼叫那個函式把它放進狀態，畫面就自動更新。所以整張圖的主張是，不管資料是來自使用者操作，還是後端 API，最後都要走同一條路：改狀態、讓 React 重畫，你永遠不自己去碰畫面。

壹、這是什麼

React 的資料流，是一套「畫面照著狀態畫、你只管改狀態」的運作方式。先講最基礎的零件：useState。當你在元件裡寫 const [count, setCount] = useState(0)，你其實一次拿到兩樣東西——第一個 count 是「現在的狀態值」（會影響畫面的一筆資料，初始是 0），第二個 setCount 是「唯一能合法改它的那扇門」。這裡有一條不能破的規矩：你不可以直接寫 count = 5 去改它，一定要呼叫 setCount(5)。原因是 React 要靠這個函式被呼叫，才知道「狀態變了、這塊畫面該重畫了」；你偷偷改變數，它根本不知道發生過什麼，畫面就不會更新。

把零件組起來，就是 React 最重要的一句話：資料是單向流動的。畫面（UI）永遠是「當前狀態」長出來的結果——狀態是 3，畫面就顯示 3。使用者在畫面上做操作（點按鈕、打字）會觸發事件，事件裡你去呼叫 setCount 改狀態，狀態一變，React 就拿新狀態重新算一次畫面該長怎樣、再把變動的部分畫上去。整個過程繞成一個固定方向的圈：狀態 → 畫面 → 事件 → 改狀態 → 新畫面，資料只往一個方向走，你從頭到尾都不會、也不該自己伸手去改畫面上的元素。這和上一課 Vue 的響應式其實是同一個大方向（都讓你只描述資料、畫面自動跟上），差別在 React 要你明確地透過 setState 宣告「我要改狀態」，而不是像 Vue 那樣改個變數就自動追蹤。

貳、為什麼業界在乎

業界在乎這條單向資料流，是因為它讓「畫面為什麼變成這樣」變得可預測、可追查。104 人力銀行《AI 人才趨勢報告》一再強調，求職者要能打通「從需求到上線」的完整應用情境，而不是只會零散語法。前端的完整情境裡，最常見的一段就是「畫面載入 → 跟後端要資料 → 顯示出來 → 使用者操作 → 再改資料」。React 的價值，是把這一整段都收攏成同一個規則：不管資料是使用者敲出來的、還是後端 API 回傳的，最後都得走 setState 這一扇門，畫面才會更新。這代表當畫面出錯時，你只要回頭看「是哪一次 setState 把狀態設成了這個值」，而不必在滿地的手動改畫面程式碼裡大海撈針。

把資料流限制成單向，換來的是團隊層級的兩個實際好處。第一是可維護：狀態是畫面的唯一真實來源，畫面只是它的投影，所以除錯時你追的是「資料怎麼變的」這一條線，而不是四散各處的畫面操作。第二是可協作：一個大頁面拆成很多小元件，每個元件各自管好自己的狀態、或從上層接收資料往下傳，資料流向清楚，多人同時改才不會互相踩到。這也是為什麼 React 在台灣中大型企業和國際遠端職缺裡幾乎是前端的預設選項——它不是語法比較短，而是它把「資料怎麼流」這件事訂成一條所有人都遵守的規矩，專案大起來才不會亂。

參、實務怎麼用

放到 91APP 這類電商、或玉山網銀的場景，最典型的例子是一個「訂單列表頁」。這種頁面的資料不是寫死的，是要跟後端 API 要的，所以標準做法是：我用 useState 準備三筆狀態——一筆放「訂單資料」、一筆放「是否載入中」、一筆放「有沒有出錯」。畫面一載入，我在 useEffect 裡發出 fetch 去打訂單 API；打之前先把「載入中」設成 true，讓畫面顯示轉圈圈；資料回來了，就 setOrders(資料) 並把「載入中」設回 false，畫面自動換成訂單列表；如果 API 掛了，就 setError(錯誤)，畫面改顯示「載入失敗，請重試」。使用者若按了「只看已出貨」的篩選鈕，我不是自己去改畫面上的清單，而是改一筆「篩選條件」狀態，讓畫面照新條件重畫。你會發現，不管資料來自 API 還是使用者操作，我從頭到尾做的都是同一件事：改狀態，剩下的交給 React 重畫。

對我這種法律金融跨域背景的人，最能講出差異化的一點，是把「單向資料流」連到狀態的三種樣貌：載入中、成功、失敗。很多初學者只想著「拿到資料、顯示出來」，卻忘了資料還沒回來、或根本要不到的那兩種狀態——在金融產品裡，這正是最不能漏的地方。使用者查詢交易明細時，如果 API 慢了三秒卻沒有任何「載入中」的提示，他會以為當掉、重複點擊；如果查詢失敗卻默默顯示空白，他會誤以為「我這個月沒有交易」，這在金融情境是會出事的誤導。我的合規直覺讓我習慣先問「這件事會怎麼失敗、失敗時該怎麼誠實告訴使用者」，剛好對上 React 這套「每種狀態都要顯式處理」的資料流設計。放到國際遠端全端職缺，同一組觀念會往後端延伸：前端這三種狀態，對應的是後端 API 該回什麼狀態碼、該怎麼設計錯誤訊息，這是我接下來要打通的下一段。

肆、常見誤區或追問延伸

最容易答錯、也最容易在實作踩到的地方，是以為「我呼叫了 setCount(count + 1)，下一行就能讀到新的 count」。這是把狀態更新當成「立刻生效」，但真相是狀態更新是非同步的：你呼叫 setCount 只是「預約」一次更新，React 會安排在稍後、重新渲染這個元件時才真正套用新值。所以你在同一個函式裡呼叫完 setCount、下一行馬上去讀 count，讀到的還是舊值。更經典的坑是「連續加三次」：如果你寫三行 setCount(count + 1)，你以為會加 3，實際上因為這三行讀到的 count 都是同一個舊值，結果只加了 1。正確做法是用「函式式更新」——setCount(prev => prev + 1)，讓 React 保證每次都拿到上一次的最新值。面試官很愛用這題確認你是「真的懂渲染時機」，還是把 setState 當成普通賦值。這裡我要誠實：這個原理和踩雷情境我搞懂了、也能講清楚為什麼，但我目前是從教學專案和小型 side project 練的，還沒在大型 React 產品裡處理過複雜的狀態管理（例如跨很多元件共享狀態、或用 Redux 這類工具管理全域狀態）；被追問到這種實戰細節時，我會講清楚我掌握的主線並說明我會怎麼查證，而不是硬掰經驗。

另一個值得先想清楚的追問，是「state」和「props」不是同一件事。state 是元件自己擁有、自己能改的資料（用 setState 改）；props 是父元件傳進來的資料，子元件只能讀、不能改。這條界線是單向資料流的延伸：資料從上往下傳（父傳子用 props），子元件想影響上層，就呼叫父元件傳下來的函式回報，而不是直接去改 props。把這兩者分清楚，才不會在被問到「資料該放在哪個元件」時答得含糊——一筆資料只有一個元件是它的「主人」，其他元件要嘛透過 props 拿到它、要嘛透過回呼函式請主人去改它。

React 的資料流，從來不是一堆要背的 API，而是一句可以貫穿全部的規矩：畫面照狀態畫，你只改狀態、讓它重畫，永遠不自己碰畫面。把這句話記牢，useState、useEffect、串 API、state 與 props 的分界，全都只是它的不同側面。

🎤 面試官可能怎麼問
  1. 「講一下 React 的資料流是怎麼運作的？」 👉 這題其實在問：你懂不懂單向資料流這個核心心智模型，還是只會拼 API。 她可以怎麼答：React 的核心規矩是畫面照著狀態畫出來的，資料是單向流動的。我用 useState 拿到一筆狀態和一個改它的函式，畫面就是這筆狀態長出來的結果。使用者操作會觸發事件，我在事件裡呼叫那個函式去改狀態，狀態一變，React 就拿新狀態重新算畫面、只更新變動的部分。整個過程繞成一個圈：狀態到畫面、事件回頭改狀態。重點是我從頭到尾都不自己去動畫面，只改狀態、讓 React 重畫。
  2. 「useState 回傳的那兩個東西分別是什麼？為什麼不能直接改狀態變數？」 👉 這題其實在問：你知不知道 setState 是 React 感知變化的唯一入口。 她可以怎麼答：useState 回傳一個陣列，第一個是現在的狀態值，第二個是專門用來改它的函式，習慣命名成 setXxx。我不能直接改那個變數，因為 React 要靠這個函式被呼叫，才知道狀態變了、該重新渲染了。如果我偷偷改變數，React 根本不知道發生過事，畫面就不會更新。所以那個函式是 React 感知變化的唯一入口，一定要走它。
  3. 「你呼叫 setCount 之後，下一行馬上讀 count，會讀到新值嗎？」 👉 這題其實在問：你懂不懂狀態更新是非同步的、有渲染時機。 她可以怎麼答：不會，讀到的還是舊值。因為狀態更新是非同步的，呼叫 setCount 只是預約一次更新，React 會安排在稍後重新渲染時才真正套上新值，所以同一個函式裡下一行讀到的仍是這次渲染的舊 count。最經典的坑是連續寫三次 setCount(count + 1)，因為三次讀到的都是同一個舊值，結果只加了一。正確做法是用函式式更新 setCount(prev => prev + 1)，讓 React 保證每次都拿到上一次的最新值。
  4. 「一個頁面要跟後端 API 拿資料，你會怎麼設計狀態？」 👉 這題其實在問：你會不會處理載入中和錯誤，而不只是拿到資料。 她可以怎麼答：我至少會準備三筆狀態：資料本身、是否載入中、有沒有出錯。畫面一載入，我在 useEffect 裡發 fetch 打 API，打之前先把載入中設成 true 讓畫面顯示轉圈圈；資料回來就把它放進狀態、載入中設回 false，畫面自動換成內容；如果失敗就設錯誤狀態，畫面改顯示載入失敗請重試。我特別在意載入中和失敗這兩種狀態，尤其在金融產品裡，API 慢了沒提示、或失敗卻默默空白，都會誤導使用者。
  5. 「state 和 props 有什麼不一樣？一筆資料該放哪？」 👉 這題其實在問：你分不分得清資料的擁有權和單向傳遞。 她可以怎麼答：state 是元件自己擁有、自己能用 setState 改的資料；props 是父元件傳進來的，子元件只能讀、不能改。這是單向資料流的延伸：資料從上往下用 props 傳，子元件想影響上層就呼叫父元件傳下來的函式去回報，而不是直接改 props。決定一筆資料放哪，我會看誰是它的主人——只有一個元件真正擁有它，其他元件要嘛透過 props 拿到、要嘛請主人去改。如果好幾個元件都要用，我就把它提到共同的父元件上。
