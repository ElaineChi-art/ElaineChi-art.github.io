從git push到上線：CI/CD管線省下的是哪一種風險

技能實驗室・每日課程 2026-08-19 約 8 分鐘 對應真專案主題：CI/CD 與部署
⚡ 30秒白話版

CI/CD 是一條「你把程式碼推上去，剩下的建置、測試、部署都自動接手」的生產線。CI（持續整合，Continuous Integration）負責每次有人 push，就自動把大家的程式碼合起來、跑測試、確認沒把東西弄壞——趁改動還小、還熱的時候抓錯，而不是等到上線前一次爆一堆。CD（持續部署／交付，Continuous Deployment/Delivery）負責把通過檢查的版本，用一套固定、可重複、能一鍵回退的方式送上線，不靠某個人記得「先關服務、再上傳、再重啟」這種手動步驟。所以它真正省下的，不是打字或部署的時間，而是「人為疏漏」這種風險：忘了跑測試、手滑漏一步、上線出包卻回不去。一句話心法：CI/CD 是把「靠人記得、靠人小心」的流程，換成「靠機器每次都一樣」的流程。

SLIDE 1 簡報講解

這張圖在講的是，從你 git push 之後，程式碼是怎麼一路被送到上線的。最上面那條生產線有四關：你把改動推上去、CI 自動建置加跑測試、CD 用固定步驟自動部署、最後才上線給使用者看。重點是中間兩關會把關，測試沒過就擋下來，不會放行。下面兩張卡是對照。左邊紅色的是靠人手動上線的樣子：可能忘了跑測試、部署七步驟手滑漏一步、在我電腦上明明可以但換環境就壞、出包想退回卻不記得上一版長怎樣。這些風險都藏在「這次剛好沒注意到」。右邊藍色的是交給 CI/CD：每次 push 強制跑測試、部署寫成腳本機器照做、同一份流程跑測試站和正式站、每個版本留紀錄能一鍵退回。所以整張圖的主張是，CI/CD 省下的不是時間，是人為疏漏這種風險，把靠人記得換成靠機器每次都一樣。

壹、這是什麼

CI/CD 是一條自動化的生產線，接在「工程師把程式碼推上去（git push）」之後，把「建置、測試、部署到上線」這些原本要靠人手動做的步驟，交給機器每次都照同一套流程跑一遍。它其實是兩件事拼起來。前半段 CI（持續整合，Continuous Integration）指的是：每當有人把改動推上共用的程式碼倉庫，系統就自動把大家的程式碼合在一起、重新建置、把測試全部跑一遍，確認這次改動沒把別的地方弄壞。重點在「持續」——不是等到快上線才一次整合，而是每天、每次小改動都整合一次，趁問題還小、還好找的時候就抓出來。

後半段 CD 是把通過檢查的版本自動、可重複地送出去。CD 有兩個很接近但不完全一樣的意思：持續交付（Continuous Delivery）是「隨時都準備好可以上線，但按不按下上線那顆按鈕由人決定」；持續部署（Continuous Deployment）則更進一步，「通過所有檢查就自動一路上到正式環境，連按鈕都省了」。不管哪一種，核心承諾都一樣：上線這件事變成一個固定、可重複、出事能一鍵退回的動作，而不是某個工程師半夜手動 SSH 進伺服器、憑記憶敲七八個指令。你可以把整條管線想成機場的行李輸送帶：包裹（你的程式碼）放上去之後，一路自動過安檢（測試）、分流、送到登機口（上線），中間哪一關不過就被攔下來退回，而不是靠一個人抱著行李用跑的、還要自己記得每個轉彎。

貳、為什麼業界在乎

業界在乎 CI/CD，是因為它把「上線」從一件提心吊膽的大事變成一件無聊的例行小事——而在軟體交付裡，「無聊」是最高的讚美。沒有 CI/CD 的團隊，上線往往是這樣：改動累積一大包，選一個「大家都在」的時段，某個資深工程師手動操作，全公司屏息看它會不會爆；一旦出事，還要臨時翻歷史、猜哪一行害的、想辦法退回去。這整套流程的風險，全押在「這次剛好沒有人出錯」上。CI/CD 解決的正是這個：它讓每次改動都小、都自動測過、都用同一套步驟上線，於是上線可以一天很多次、每次都很小、出事影響範圍也小、還能立刻回退。這不是玄學，是這幾年業界公認的工程實務方向，也是「能不能穩定交付」的分水嶺。

這件事也剛好對上 104 人力銀行《AI 人才趨勢報告》一直強調的「打通完整應用情境」——它把 CI/CD 這類「自動化流程」列為需求成長最快的方向之一，重點正是求職者要能連起整條交付流程，而不是只會孤立地寫功能。CI/CD 就是後端與全端「完整情境」裡很典型的最後一段：你不只是會把功能寫出來、在自己電腦上跑得動，而是能想到——這段程式怎麼自動被測試、怎麼被安全地送上正式環境、萬一上線出包怎麼在幾分鐘內退回。一個只會在本機把功能做完就喊「好了」的人，和一個會接著問「這要怎麼安全上線、壞了怎麼退回」的人，在面試桌上的成熟度差很多。前者交的是一段程式碼，後者交的是一段能被團隊反覆、安全地送到使用者手上的流程。

參、實務怎麼用

放到玉山網銀或 91APP 這類產品，假設我做完一個功能、要讓它上線，有了 CI/CD 之後大致會是這樣。第一步，我把改動推到一個新分支、開一個合併請求（Pull Request，請團隊把我的分支併回主線前先審查）。這一推，CI 就自動被觸發——例如用 GitHub Actions 這類工具，照著我們寫好的設定檔，自動幫我安裝環境、建置、把單元測試整批跑過。如果測試有一條沒過，或有人動到的地方壞了，PR 上會直接標紅、擋住不給合併，我當下就知道要修，而不是等它上線炸給使用者看。第二步，等我修到全綠、也通過同事 code review，改動併進主線。這時 CD 接手：把這個通過檢查的版本，用固定腳本自動部署到預備環境（staging，一個跟正式環境長得幾乎一樣、給人先試的站），確認沒問題後再上正式站——像金融這種高風險場景，最後這一步通常會保留「由人按一下確認」的閘門，也就是持續交付而非全自動部署。第三步，萬一上線後才發現有狀況，因為每個版本都有紀錄、部署又是可重複的動作，我可以一鍵回退到上一個好的版本，把災情控制在幾分鐘內，而不是手忙腳亂地反向操作。

對我這種法律金融跨域背景的人，CI/CD 最能連回本業直覺的一點，是它本質上是一套「稽核軌跡＋內控」的工程版本。做合規、做內控時你最在意的往往不是「這次有沒有做對」，而是「這件事有沒有一套每次都會被強制執行、而且留得下紀錄可回溯的流程」——不能靠某個人今天心情好、記性好。CI/CD 的精神完全一樣：測試是「上線前一定會被跑、不能跳過的檢查關卡」，部署腳本是「白紙黑字、機器照做、不會因人而異的標準作業程序」，版本紀錄則是「誰在什麼時候上了什麼、出事能查」的軌跡。放到金融系統，這種「流程強制、可回溯、可回退」的要求特別要命，因為改壞的東西動到的是真金白銀和法遵責任。放到國際遠端全端職缺也很加分——遠端團隊沒辦法圍在一台電腦前一起盯著上線，所以更需要靠一條自動化管線，讓「上線」這件事不依賴任何人剛好在線上、剛好記得步驟。能講清楚「我為什麼要用 CI/CD、它幫團隊擋掉了哪種風險」，本身就是專業度的證明。

肆、常見誤區或追問延伸

最容易踩、也最常被追問的坑，是把「有了 CI/CD」等於「不會出事」。CI/CD 不是一個保證品質的魔法，它只是一台忠實的執行機器：它會每次都乖乖跑你叫它跑的測試——但如果你的測試本來就寫得很淺、根本沒涵蓋到會出錯的地方，那管線再自動、再快，也只是又快又穩地把爛東西送上線而已。CI/CD 的價值上限，是由你的測試品質和部署設計決定的；它保證的是「流程每次都一樣、沒有人為漏步」，不是「程式一定對」。正確的講法是：CI/CD 消滅的是「疏漏型」的風險（忘了測、漏了步、退不回），不是「你根本沒想到的 bug」。如果面試官問「那有了 CI/CD 是不是就不會有線上事故了」，能回答「不會，它保證的是流程一致與可回退，程式對不對還是取決於測試寫得夠不夠、以及我們對變更的謹慎」，就是懂門道的答法。

另一個很值得先想清楚的分界，是「CI/CD 跟寫一個自動化部署腳本，差在哪？」。乍看很像——都是「用程式自動做本來手動的事」，好像寫個一鍵部署的 shell script 就叫 CI/CD 了。但差別在「持續」與「把關」這兩個字：CI/CD 的重點不只是「自動執行」，而是每一次改動都自動被整合、被測試把關、被記錄，通過了才放行下一關——它是一條有檢查閘門、有觸發條件、有回退機制的流水線，不是一顆你想到才手動去按的按鈕。一個只會「自動」但不會「把關」的腳本，跟 CI/CD 的精神其實是兩回事。不過我要誠實說：這一題我理解原理、也能講清楚 CI 跟 CD 各自在解決什麼、為什麼要有測試閘門和回退機制，但目前主要是在自己的小專案上用過像 GitHub Actions 這種現成工具接測試與自動部署，還沒在真正大團隊、多環境、要處理資料庫遷移（migration）、藍綠部署或上線出事應變這種生產規模的管線裡實戰過；被追問到那個層級時，我會誠實說明我掌握的原理與會怎麼上手，而不是硬掰經驗。

把功能寫出來、在自己電腦上跑得動，只是交付的一半；另一半是它能不能每次都用同一套、測過、可回退的流程被安全地送到使用者手上。CI/CD 真正省下的從來不是打字或部署的那幾分鐘，而是「這次剛好有人忘了、剛好漏了一步、剛好退不回去」的那種風險——它把靠人記得、靠人小心的流程，換成靠機器每次都一樣。

🎤 面試官可能怎麼問
  1. 「你可以用白話解釋一下什麼是 CI/CD 嗎？」 👉 這題其實在問：你是真的懂它在解決什麼，還是只會背「持續整合、持續部署」這幾個字。 她可以怎麼答：CI/CD 是接在 git push 之後的一條自動化生產線。CI 是持續整合，每次有人把改動推上去，系統就自動把程式碼合起來、重新建置、把測試全部跑一遍，趁改動還小的時候就抓出有沒有把東西弄壞。CD 是持續交付或部署，把通過檢查的版本用一套固定、可重複、能一鍵回退的流程送上線，不靠某個人手動記得每個步驟。它真正的價值不是省打字時間，而是把「靠人記得、靠人小心」的上線流程，換成「靠機器每次都一樣」，消滅掉忘了測、漏了步、退不回這類人為疏漏的風險。
  2. 「CI 跟 CD 差在哪？」 👉 這題其實在問：你分不分得清「把關」跟「送出」是管線的兩段不同工作。 她可以怎麼答：CI 管的是前半段——整合跟把關。每次改動推上來就自動建置、跑測試，確認沒把別的地方弄壞，重點在「趁早、每次都測」。CD 管的是後半段——把通過檢查的版本自動、可重複地送上線。CD 還細分兩種：持續交付是隨時準備好可以上線、但按不按上線由人決定；持續部署是通過所有檢查就自動一路上到正式環境。簡單說 CI 負責「這版能不能上」，CD 負責「怎麼把它安全地送上去、出事怎麼退回」。
  3. 「有了 CI/CD 是不是就不會有線上事故了？」 👉 這題其實在問：你會不會過度神化工具，懂不懂它的能力邊界。 她可以怎麼答：不會。CI/CD 是一台忠實的執行機器，它保證的是流程每次都一樣、沒有人為漏步、而且出事能回退，但它保證不了程式一定對。如果測試本來就寫得很淺，沒涵蓋到會出錯的地方，那管線只是又快又穩地把爛東西送上線而已。所以它消滅的是「疏漏型」的風險——忘了測、漏了步、退不回——不是那種你根本沒想到的 bug。它的價值上限，是由測試品質和部署設計決定的。
  4. 「那 CI/CD 跟自己寫一個一鍵部署腳本，差在哪？」 👉 這題其實在問：你懂不懂 CI/CD 的核心不只是「自動」，還有「持續」跟「把關」。 她可以怎麼答：差在「持續」跟「把關」。一個部署腳本是你想到才手動去按的一顆按鈕，只做「自動執行」。CI/CD 是一條每一次改動都會被自動觸發、被測試閘門把關、被記錄，通過了才放行下一關的流水線，還帶回退機制。重點不只是自動做完，而是每次改動都強制走同一套檢查、留下軌跡。所以一個只會自動、不會把關的腳本，跟 CI/CD 的精神其實是兩回事。
  5. 「你實際上有用過哪些 CI/CD 工具？做到什麼程度？」 👉 這題其實在問：你的經驗是紙上談兵還是真的動過手，而且你誠不誠實。 她可以怎麼答：老實說我目前主要是在自己的小專案上用過 GitHub Actions，接了推上去自動跑測試、還有簡單的自動部署，所以 CI 跟基本 CD 的流程和它在解決什麼問題我是清楚的。但我還沒在大團隊、多環境、要處理資料庫遷移、藍綠部署或上線出事應變這種生產規模的管線裡實戰過。如果這份工作會碰到那個層級，我會先讀懂團隊現有的管線設定和上線流程，從跟著跑一次完整部署、看它每一關在檢查什麼開始上手，而不是一來就大改。
