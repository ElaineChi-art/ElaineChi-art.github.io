pandas 的資料處理心法：一行程式碼背後的向量化思維

技能實驗室・每日課程 2026-08-30 約 8 分鐘 對應真專案主題：Python 進階套件
⚡ 30秒白話版

在 pandas 裡自己寫 for 迴圈一列一列處理資料，往往比一行向量化寫法慢上幾十倍——這不是因為你程式寫得爛，而是 Python 這種語言逐列跑本來就慢。向量化（vectorization，把「對整欄做同一件事」當成一個指令交給底層一次算完）的核心思維是：不要想「這一列怎麼算」，要想「這一整欄要做什麼變換」。當你寫 df['金額'] * 1.05，你不是在跑一個 Python 迴圈，而是把整欄丟給底層用 C 寫好的迴圈一次處理完，資料在連續的記憶體上批次運算，速度天差地遠。一句話：向量化不是語法糖，而是把運算從慢的 Python 這層，搬到快的 C 那層去跑。學會這個思維，你寫的資料處理程式會又短又快，面試被問到「為什麼不要在 pandas 裡寫迴圈」時也答得出真正的原因。

SLIDE 1 簡報講解

這張圖在講的是，pandas 為什麼要你少寫 for 迴圈、改用向量化。左邊是逐列迴圈的做法：Python 一列一列地跑，每一步都要在 Python 這層解譯、拆箱再裝箱，資料一大就慢得離譜。右邊是向量化：你把「對整欄做同一件事」當成一個指令交給 pandas，底層由 NumPy 用 C 寫好的迴圈一次跑完，資料在連續的記憶體上批次處理，速度常常差到幾十倍。關鍵的思維轉換是，不要想這一列怎麼算，要想這一整欄要做什麼變換。你描述的是要做什麼，把怎麼跑得快交給底層。記住一句話：向量化不是語法糖，是把運算從 Python 這層搬到 C 那層。

壹、這是什麼

先講結論：向量化就是「對整欄資料下一個指令，讓底層一次算完」，而不是自己寫 Python 迴圈一列一列處理。舉個最小的例子：你有一欄「金額」，要每筆都乘上 1.05（加 5% 手續費）。土法煉鋼的寫法是開一個 for 迴圈，一列一列取出數字、乘完再塞回去；向量化的寫法只有一行 df['金額'] * 1.05。兩種做法算出來的結果一樣，但底層跑的方式完全不同。

差別在於「這行程式碼實際上是誰在跑」。你寫 Python 迴圈時，是 Python 這個直譯器一列一列地跑——每一步它都要重新解譯這行指令、把數字從 Python 物件拆箱出來、算完再裝箱回去、順便做型別檢查。這些固定開銷本身不大，但你有幾百萬列，它就重複幾百萬次。而向量化的一行，其實是把整欄資料交給 pandas 底層的 NumPy，由它用 C 語言早就編譯好的迴圈一次跑完，中間完全不回到 Python 這層。

所以向量化真正的心法，是一個思維上的轉向：不要想「這一列怎麼算」，要想「這一整欄要做什麼變換」。你不是在指揮電腦「先做第一列、再做第二列」，而是在描述「這一整欄乘以 1.05」「這兩欄相加」「這一欄裡符合某條件的挑出來」。你負責描述「要做什麼」，把「怎麼跑得快」交給底層。想通這件事，你會發現大部分資料清洗其實都能寫成幾個整欄變換的組合，程式又短又快。

貳、為什麼業界在乎

業界在乎，是因為資料量一大，向量化與否的差距會從「差一點」變成「能不能跑完」。在量級上，向量化寫法比逐列 Python 迴圈快上數十倍是很常見的事，資料越大差距越明顯（這是 pandas／NumPy 生態的常識性技術知識，實際倍數會依運算種類、資料型別而變，不是固定數字）。原因前面講過：省掉的不是「算」的時間，而是「一列一列反覆進出 Python 直譯器」的固定開銷。當你要處理的是一天幾百萬筆交易紀錄，這個差距就是「跑三秒」跟「跑五分鐘」的差別，甚至是記憶體撐不撐得住的差別。

更重要的是，這正是「打通完整應用情境」而不是「零散學單一語法」的分水嶺。104 人力銀行《AI 人才趨勢報告》一再強調企業要的是能把技術接到真實資料流程的人，而不是只會背 API 的人。會呼叫 pandas 的人很多，但能講清楚「為什麼這樣寫會慢、慢在哪一層、該怎麼改」的人，才是真的能在正式資料管線裡把效能問題解掉的人。資料清洗、特徵工程、報表產出，這些都是機器學習與分析專案的地基——地基寫得慢又吃記憶體，後面全都卡住。向量化思維就是讓你有能力在這個地基上寫出跑得動、也維護得動的程式。

參、實務怎麼用

放到玉山、國泰這類金融科技，或 91APP 這種電商，向量化最常出現在「大批資料要做同一種變換」的場景。舉一個貼近我背景的例子：假設我在銀行做對帳與交易清洗——手上有一整個月、上百萬筆的信用卡交易，我要算每筆的實收金額（原金額扣掉分潤與手續費）、把外幣交易依當日匯率換算成台幣、再把「可疑」的交易依幾個條件標記出來。如果我一列一列跑 for 迴圈，光是換算那一步就可能跑到讓人不想等。改成向量化，我會把「扣手續費」寫成整欄相乘、把「換匯」寫成兩欄相乘、把「標記可疑」寫成一個布林條件（df[df['金額'] > 門檻]）去篩選——每一步都是對整欄下指令，整批一次算完。

所以我實務上會這樣做，面試時也這樣講：先問自己「這個操作能不能寫成對整欄的變換」，能的話就絕不寫迴圈。對我這種法律金融跨域背景的人，這裡有個好懂的類比：向量化很像「發一份統一格式的公文給全部門，一次處理完」，逐列迴圈則像「把每個人的案子一件一件叫進來、當面辦完再叫下一個」——後者每一件都要重新招呼、確認身分、收尾，光是這些例行動作累積起來就慢得驚人。不過要注意，這個類比是幫助理解「固定開銷 × 次數」的直覺，真正讓向量化快的是底層 C 迴圈與連續記憶體，不是「一次辦很多件」這麼簡單。

肆、常見誤區或追問延伸

最常見、乍看懂了其實會答錯的誤區，是以為「用了 df.apply() 就是向量化了」。這是很多人踩的坑。apply 的寫法看起來很像一行、很「pandas」，但它骨子裡多半還是一列一列地在 Python 這層呼叫你給的那個函式——它是把迴圈藏起來，不是把迴圈搬到 C 那層。所以 apply 通常只比手寫 for 迴圈快一點點，跟真正的向量化（整欄的算術、比較、內建字串／時間方法）差一個量級。被追問時要能一句切中：真正的向量化是「整欄運算下沉到 NumPy 的 C 迴圈」，而 apply 大多數情況只是語法上包裝過的逐列呼叫，效能不能混為一談。

另一個容易被追問到卡住的點是：「那是不是所有情況都該向量化？向量化有沒有代價？」——這題想聽的是你知不知道它的邊界，而不是把它當萬靈丹。要能講清楚兩件事：第一，向量化通常會一次把整欄的中間結果都算出來、放進記憶體，所以它是拿記憶體換速度；資料大到記憶體吃緊時，反而要考慮分塊處理或改用別的工具。第二，有些邏輯天生就是「這一列的結果依賴上一列」（例如某些逐筆累積、狀態機式的計算），這種順序相依的運算很難純向量化，硬湊反而讓程式難懂。我要誠實說：向量化的原理、為什麼快、跟 apply 的差別，這些我已經能清楚講明白；但真正拿幾百萬列的資料去實測不同寫法的時間與記憶體、抓出哪一步是瓶頸的完整實戰，我目前是懂概念、動手還不多。真被追問到那個層級，我會把邊界講清楚、說明我會怎麼用計時與記憶體量測一步步驗證，而不是宣稱有我還沒有的經驗。

pandas 的向量化教會我一件事：寫資料處理程式時，別再想著「怎麼一列一列跑」，改成問「這一整欄要做什麼變換」——記住一句話，向量化不是語法糖，是把運算從慢的 Python 這層，搬到快的 C 那層。

🎤 面試官可能怎麼問
  1. 「為什麼在 pandas 裡不要自己寫 for 迴圈一列一列處理？」 👉 這題其實在問：你懂不懂慢的原因是「逐列進出 Python 直譯器」的固定開銷。 她可以怎麼答：因為 Python 逐列跑本來就慢，慢的不是計算本身，而是每一列都要重新在 Python 這層解譯指令、把數字拆箱裝箱、做型別檢查，這些固定開銷乘上幾百萬列就很可觀。向量化的一行是把整欄交給底層 NumPy，用 C 早就編譯好的迴圈一次跑完，中間不回到 Python 這層，資料又放在連續記憶體上批次算。所以同一件事，向量化寫法在量級上常常快幾十倍，資料越大差越多。一句話，向量化是把運算從慢的 Python 層搬到快的 C 層。
  2. 「向量化到底是什麼？跟寫迴圈算出來的結果不是一樣嗎？」 👉 這題其實在問：你知不知道結果一樣但底層執行方式完全不同。 她可以怎麼答：結果一樣，但底層跑的方式完全不同，這正是重點。向量化是對整欄下一個指令，例如整欄乘 1.05、兩欄相加、用一個布林條件篩選，這些操作會下沉到 NumPy 的 C 迴圈一次算完。手寫迴圈則是 Python 直譯器一列一列跑。思維上的差別是，我不再想「這一列怎麼算」，而是想「這一整欄要做什麼變換」，我負責描述要做什麼，把怎麼跑得快交給底層。大部分資料清洗其實都能拆成幾個整欄變換的組合。
  3. 「那我用 df.apply() 是不是就等於向量化了？」 👉 這題其實在問：你分不分得清 apply 是包裝過的逐列呼叫，不是真向量化。 她可以怎麼答：不是，這是很常見的誤會。apply 看起來像一行、很 pandas，但它骨子裡多半還是一列一列在 Python 這層呼叫我給的函式，它只是把迴圈藏起來，沒有把迴圈搬到 C 那層。所以 apply 通常只比手寫 for 迴圈快一點，跟真正的向量化差一個量級。真正的向量化是整欄的算術、比較、內建的字串或時間方法，那些才會下沉到 C。我會盡量把邏輯改寫成整欄運算，只有真的沒辦法向量化時才退而用 apply。
  4. 「向量化有沒有代價？是不是所有情況都該用？」 👉 這題其實在問：你知不知道它拿記憶體換速度、以及順序相依運算的限制。 她可以怎麼答：向量化不是萬靈丹，主要有兩個邊界。第一，它通常會一次把整欄的中間結果都算出來放進記憶體，等於是拿記憶體換速度，資料大到記憶體吃緊時反而要考慮分塊處理。第二，有些邏輯天生是這一列依賴上一列的結果，像某些逐筆累積或狀態機式的計算，這種順序相依很難純向量化，硬湊反而讓程式難懂。所以我的原則是：能寫成整欄變換的就向量化，遇到順序相依或記憶體受限的情況再另想辦法。
  5. 「你實際用 pandas 處理過多大的資料、做過效能調校嗎？」 👉 這題其實在問：你是真的動手實測過，還是只懂原理，誠實度也在被看。 她可以怎麼答：我要誠實說，向量化的原理、為什麼快、跟 apply 的差別，這些我已經能清楚講；但拿幾百萬列的真實資料去實測不同寫法的時間跟記憶體、抓出哪一步是瓶頸，這種效能調校的完整實戰我動手經驗還不多。如果要我上手，我會先用計時工具量每一步花多久、用記憶體量測看哪一步吃最兇，把逐列迴圈的地方逐一改成整欄向量化再比較前後差距，一步步用數據驗證，而不是宣稱有我還沒有的經驗。
