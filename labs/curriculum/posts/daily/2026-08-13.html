讓介面感覺「活著」：CSS transition/animation的分寸拿捏

技能實驗室・每日課程 2026-08-13 約 7 分鐘 對應真專案主題：CSS動畫實作
⚡ 30秒白話版

CSS 的 transition 和 animation，是讓畫面變化不要「瞬間跳」而是「平順滑過去」的兩個工具。transition（過渡）管的是「從一個狀態滑到另一個狀態」，需要有東西觸發它——例如滑鼠移上去、按鈕顏色慢慢變。animation（動畫）加上 @keyframes 就更強：可以自己跑、可循環、能有很多階段，例如載入中一直轉圈。但這一課真正的重點不是語法，而是分寸：動效是為了幫使用者理解「剛剛發生了什麼、東西從哪來到哪去」，不是拿來炫技。三個原則記牢：時間抓在大約 150–300ms、盡量只動 transform 和 opacity（效能最好），還要尊重使用者的「減少動態」偏好設定。

SLIDE 1 簡報講解

這張圖在講的是，CSS 動畫真正該拿捏的分寸在哪裡。左邊先分清楚兩個工具：transition 管的是從一個狀態滑到另一個狀態的過渡，需要有觸發，比如滑鼠移上去顏色慢慢變；animation 加上 keyframes 可以自己跑、可以循環、可以有很多階段，比如載入中的轉圈。中間是最重要的三個分寸原則：時間抓在大約一百五到三百毫秒之間，太慢會讓人等；盡量只動 transform 和 opacity 這兩個屬性，因為它們走的是合成器、不會重算版面，畫面才不會卡；還要尊重使用者的減少動態偏好設定，關掉多餘動畫。右邊提醒常見的坑，像是對 display none 做過渡是沒有效果的。整張圖的主張是：動畫是為了幫使用者理解畫面發生了什麼，不是拿來炫技。

壹、這是什麼

transition 和 animation，都是讓 CSS 屬性的變化「有時間感」的工具——差別在誰來啟動、能不能自己跑。平常你改一個 CSS 屬性（例如把按鈕背景從灰變藍），畫面是瞬間切換的；transition（過渡）做的事，就是叫瀏覽器「別瞬間切，給我用一段時間平順地補間過去」。但 transition 有個前提：它只在屬性值真的改變的那一刻才作用，所以一定要有東西去觸發那個改變——最常見的是滑鼠移上去（:hover）、或用 JavaScript 加減一個 class。它是「一次性、來回式」的：狀態變過去、再變回來。

animation（動畫）則更進一步：它讓你先用 @keyframes 把一段變化拆成好幾個階段（0% 長這樣、50% 長那樣、100% 又長這樣），然後這段動畫可以自己開始播、自動循環、不需要任何觸發。載入中一直轉的圈圈、緩緩呼吸的提示點，都是 animation。一句話記住兩者的分工：transition 管「從 A 狀態滑到 B 狀態」的過渡、需要觸發；animation 管「會自己跑、可循環、有多個階段」的動畫。簡單的 hover 回饋用 transition 就夠了，別動不動就搬出 animation。

貳、為什麼業界在乎

業界在乎動效，是因為它其實是「介面回饋」，不是裝飾——它在降低使用者的不確定感。人點了一個按鈕，如果畫面毫無反應地瞬間跳到下一頁，他會懷疑「我剛剛到底有沒有點到」；如果按鈕微微下沉、頁面平順地滑進來，他就知道系統收到了、事情正在發生。動效幫使用者建立「東西從哪來、到哪去」的空間感：抽屜是從左邊滑出來的，關掉時就該滑回左邊，而不是憑空消失。這正接回 104 人力銀行《AI 人才趨勢報告》一直強調的方向——求職者要能打通「從需求到體驗」的完整應用情境，而不是只會孤立地寫 @keyframes 語法。懂得「這個動效是為了解決什麼體驗問題」，比會背十種動畫寫法更值錢。

另一個業界很在乎、而且很吃基本功的點是效能。動畫如果做錯，畫面會一格一格地卡（掉幀）。關鍵原理是：瀏覽器渲染畫面有幾個階段，只有動 transform（位移、縮放、旋轉）和 opacity（透明度）這兩類屬性，能交給繪圖合成器（compositor）直接處理、不必重新計算版面；而如果你去動 width、height、top、left 這種會改變元素位置或大小的屬性，瀏覽器每一幀都得重新排一次版（reflow／重排），一卡就是整頁跟著卡。所以「想讓某個東西往右移」的正解，是用 transform: translateX() 而不是改 left。這種「知道為什麼順、為什麼卡」的判斷，是台灣中大型企業和國際遠端前端職缺都會拿來確認你到底懂不懂底層的題目。

參、實務怎麼用

放到玉山網銀或 91APP 這類產品，動效最常出現在四種場景：hover 回饋、狀態切換、載入等待、頁面／面板轉場。我的做法會是這樣分：按鈕滑上去變色、加入購物車時圖示輕輕放大一下——這種「有觸發、來回一次」的，用 transition，時間設短，大約 0.2s，加一點 ease-out 讓它結尾自然收住。而資料還在跟後端要、畫面得先撐著的載入狀態，我會用 animation 做一個會自動循環的骨架屏（skeleton）微光效果或轉圈，因為它需要「沒有觸發也自己一直跑」。表單送出後欄位驗證錯誤時，讓那一欄輕微左右抖一下提示，用 @keyframes 定義三四個位移階段、只播一次。整個過程我會刻意只動 transform 和 opacity，把每個動效控制在使用者「感覺順、但說不出哪裡有動畫」的程度。

對我這種法律金融跨域背景的人，最能連回本業的一點，是把動效理解成「程序上的告知」，而不是視覺特效。這跟我讀合約、處理金融流程時很在意的「程序正義」其實同一個直覺：每一步都要讓當事人清楚知道「你的動作被收到了、現在進行到哪、下一步會發生什麼」。金融產品尤其不能讓使用者對「我剛剛那筆轉帳到底送出去了沒」產生一秒鐘的懷疑——所以送出鈕按下後要立刻有回饋、載入時要有明確的進行中狀態、成功要有一個安定人心的確認動效。放到國際遠端全端職缺，這套「動效＝告知」的思路還會往無障礙延伸：我不能假設每個人都想看動畫，得尊重系統的「減少動態」設定——這正是下一段要講的誠實邊界。

肆、常見誤區或追問延伸

最容易踩、也最常被追問的坑，是「想用 transition 讓一個 display:none 的東西淡入淡出，結果完全沒效果」。原因是 display 這個屬性沒有「中間值」可以補間——它只有 none 和 block 這種是非題狀態，瀏覽器沒辦法在「不存在」和「存在」之間插出一個 50%，所以 transition 對它無效，元素會直接啪一聲出現或消失。正解是改用能補間的屬性：用 opacity 從 0 到 1 做淡入淡出，需要「淡出後真的不佔位、也不能被點到」的話，再搭配 visibility 一起處理。現代 CSS 也有 @starting-style 這類新語法能更漂亮地處理「元素剛出現時的起始狀態」，不過我要誠實：這個坑背後的原理我搞懂了、也能講清楚為什麼 display 不能被 transition，但更新的 @starting-style 我目前只在小 side project 試過、還沒在正式產品裡大量用；被追問到更細的瀏覽器相容或實戰細節時，我會講清楚我掌握的主線、並說明我會怎麼查文件驗證，而不是硬掰。

另一個值得先想清楚的追問，是「動畫到底要做多少才合適」。答案是克制：動效是為了幫使用者理解，一旦每個元素都在動、都在閃，注意力就被分散，反而降低了可用性、也拖慢效能。判斷標準很簡單——「這個動畫是在解釋一件事，還是只是想讓人覺得酷？」能解釋（東西從哪來、狀態變成了什麼）就留，純炫技就拿掉。而且一定要記得無障礙這一關：有些人會因為前庭功能問題，看到大幅度動畫而暈眩，作業系統提供了「減少動態」的偏好設定，我們該用 @media (prefers-reduced-motion: reduce) 去偵測它、對這些使用者關掉或大幅減弱動畫。會主動講到這一點，面試官會知道你想的是「所有使用者」，而不只是自己螢幕上好不好看。

動效這件事，講到底不是「會不會寫 @keyframes」，而是一句克制的判斷：好的動畫讓人「感覺不到動畫、只覺得順」——它在幫人理解畫面發生了什麼，不是搶戲。把 transition 和 animation 的分工、時間短、只動 transform／opacity、尊重 reduced-motion 這幾條記牢，剩下的都只是它的不同側面。

🎤 面試官可能怎麼問
  1. 「transition 和 animation 差在哪？你什麼時候用哪個？」 👉 這題其實在問：你分不分得清「需要觸發的一次性過渡」和「會自播的動畫」。 她可以怎麼答：transition 管的是從一個狀態滑到另一個狀態的過渡，它需要有東西觸發，比如滑鼠 hover 或用 JS 切 class，而且是一次性、來回式的。animation 加上 @keyframes 就能把變化拆成很多階段，可以自己開始播、自動循環，不需要觸發。所以簡單的 hover 變色、按鈕回饋我用 transition 就夠；載入中一直轉的圈圈、需要多階段或循環的，才用 animation。我不會小事也搬出 animation。
  2. 「為什麼做動畫盡量只動 transform 和 opacity？」 👉 這題其實在問：你懂不懂為什麼有些動畫會卡、有些會順。 她可以怎麼答：因為瀏覽器渲染分幾個階段，transform 和 opacity 這兩類可以直接交給繪圖合成器處理，不用重新算版面。如果我去動 width、height、top、left 這種會改變元素大小或位置的屬性，瀏覽器每一幀都要重新排一次版，也就是重排，動畫就會一格一格地卡。所以想讓東西往右移，我會用 transform translateX，而不是改 left。這樣才能維持順暢的幀率。
  3. 「我想讓一個 display:none 的元素淡入，寫了 transition 卻沒反應，為什麼？」 👉 這題其實在問：你知不知道 display 不能被補間這個經典坑。 她可以怎麼答：因為 display 沒有中間值可以補間，它只有 none 和 block 這種是非狀態，瀏覽器沒辦法在不存在和存在之間插出一個中間值，所以 transition 對它無效，元素會直接啪一聲出現。正解是改用能補間的屬性，用 opacity 從 0 到 1 做淡入淡出；如果淡出後還要它不佔位、不能被點到，再搭配 visibility 一起處理。現代 CSS 也有 @starting-style 能更漂亮地處理起始狀態，不過那部分我還在學。
  4. 「動畫的時間長度你怎麼抓？」 👉 這題其實在問：你有沒有實際手感，還是隨便填數字。 她可以怎麼答：一般的介面回饋我會抓在大約 150 到 300 毫秒之間。太快會讓人看不出有過渡、太慢會讓人覺得在等、覺得卡。小範圍的 hover 回饋我會偏短，大一點的面板轉場可以稍微長一點但也不會超過太多。緩動我常用 ease-out，讓動畫結尾自然收住，感覺比較順。重點是使用者要感覺順，但幾乎意識不到有動畫在跑。
  5. 「做動效時你會考慮無障礙嗎？」 👉 這題其實在問：你想的是所有使用者，還是只有自己螢幕上好不好看。 她可以怎麼答：會。有些使用者會因為前庭功能問題，看到大幅度動畫而暈眩，作業系統提供了「減少動態」的偏好設定。我會用 @media prefers-reduced-motion: reduce 去偵測它，對這些使用者關掉或大幅減弱動畫。這也提醒我一個原則：動效是為了幫使用者理解，不是每個地方都要動，會分散注意力又傷效能的純炫技動畫我會拿掉。誠實說，我目前是在個人專案裡實作過這個判斷，還沒在大型正式產品的完整無障礙流程裡跑過。
